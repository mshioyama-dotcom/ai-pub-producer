## 1. 改修の背景と目的

### 1.1 背景

現状のSTEP2は「書籍プロファイル(キーワード3軸含む)を元にAmazon検索結果を見て市場評価する」構成になっているが、以下の課題がある。

- STEP1で出力する「検索キーワード3軸」が、Amazon検索の実態と乖離している(著者目線の独自概念になりがち)
- キーワード候補3個では選択肢が少なく、消去法での選定になる
- レビュー数ベースの評価だけでは需要・競合・読者意図の判定が不十分
- 受講生がAmazon検索結果を手動確認する負担が大きい
- STEP2の役割が広すぎる(キーワード評価+書籍プロフ確定)

### 1.2 改修の方針

「人が判断 → AIが整理 → 人が判断」の構造を3段階で実装する。

**段階1: 人が判断**
- STEP1で書籍コンセプトを設計(草案)

**段階2: AIが整理**
- STEP2でAmazon APIから市場データ取得→キーワードスコアリング
- STEP3でレビュー分析→差別化ポイント抽出

**段階3: 人が判断(明示的な確定アクション)**
- 受講生がSTEP3完了後に「書籍プロファイルを確定する」ボタンを押下
- このまま確定 / STEP1に戻って修正 / 確定版を編集してから保存 を選択可能

### 1.3 PoC検証で確認できた事項

1. キーワード「副業 始め方」で331件ヒット、1ページ46件取得可能
2. キーワード「40代 キャリア 不安」で6件ヒット、ニッチ判定可能
3. Top Product Reviewsで日本語レビュー本文を完全取得
4. rating_distributionで★1〜★5の件数分布が一括取得可能
5. すべてVerified Purchase付きレビューで信頼性高い

### 2.2 番号がずれる理由

旧STEP2(1個)が廃止され、新STEP2/3(2個)が追加されるため、差分は実質+1。

```

新: STEP1 → [新STEP2] → [新STEP3] → STEP4 → STEP5 → ... → STEP10
                ↑ここで2つ追加
```

旧STEP3「エピソードインタビュー」が新STEP4になる、旧STEP9「Amazon説明文作成」が新STEP10になる、という「+1」のずれが全STEPに発生する。

## 4. STEP2: キーワード絞り込み(新規)

### 4.1 役割

STEP1の草案を入力として、Amazon検索で実際に使われるキーワード候補を10個生成し、3軸でスコアリングして上位1〜2個に絞り込む。

**重要1**: STEP2は書籍プロファイルを「確定」しない。市場検証フェーズの第1段階として、キーワード戦略を決めるだけ。

**重要2(v4で明確化)**: STEP2は**相談機能を実装しない**。理由はAmazon実データに基づく客観分析のため、外部AIで評価できない領域だから。代わりにAI判定アシスト(機械的なスコア判定)で受講生の判断を支援する。

### 4.2 受講生の操作フロー

```
1. STEP1の出力(草案)を確認
2. 「キーワード分析実行」ボタンを押す
3. 1〜2分待つ
4. スコア表を確認
5. 判断:
   5a. スコアが良好 → 上位1〜2個を選択 → 「STEP3へ進む」
   5b. スコアが低い → 「STEP1に戻る」を選択
```

### 4.3 裏側の処理フロー

```
[入力] STEP1の草案
   ↓
[処理1] LLMでキーワード候補10個生成
   ↓
[処理2] 各キーワードでProduct Search API呼び出し(10並列)
   - エンドポイント: /search
   - パラメータ: query=キーワード, country=JP, page=1
   ↓
[処理3] 取得データの整形
   - 上位本のタイトル、ASIN、レビュー数、★評価、発売日、出版社、KU対応
   - 発売予定日(未来日付)のものは除外
   ↓
[処理4] 機械スコアリング(相対値ベース)
   - 需要スコア: total_products・新刊比率から算出
   - 競合スコア: レビュー数中央値・個人著者比率から算出
   ↓
[処理5] LLMで意図合致スコア判定
   ↓
[処理6] 合計スコア計算 + 上位2個にAI推奨マーク付与
   ↓
[処理7] 戻り判定アシスト
   - 推奨キーワード数が0個 → STEP1に戻る推奨を表示
   - 推奨キーワード数が1個以上 → STEP3へ進む推奨を表示
   ↓
[処理8] STEP1への戻り時フィードバック生成(戻り推奨時)
   ↓
[出力] スコア表JSON + 上位本データ(STEP3で再利用) + 戻り判定結果
```

### 4.4 使用するAPIエンドポイント詳細

**Product Search**

- ベースURL: `https://real-time-amazon-data.p.rapidapi.com`
- パス: `/search`
- HTTPメソッド: GET
- 認証ヘッダー:
  - `x-rapidapi-key`: APIキー(環境変数)
  - `x-rapidapi-host`: `real-time-amazon-data.p.rapidapi.com`

**必須・推奨パラメータ**

| パラメータ | 値 | 説明 |
|------|------|------|
| query | キーワード文字列 | 必須 |
| country | `JP` | 日本Amazon |
| page | `1` | 1ページで40〜50件取得可能 |
| sort_by | (未指定) | RELEVANCEがデフォルト |
| is_prime | `false` | Kindle本のため不要 |

**取得できる主要フィールド(PoC実測ベース)**

```json
{
  "asin": "B0XXXXXXXX",
  "product_title": "本のタイトル",
  "product_price": "￥0",
  "product_star_rating": "4.7",
  "product_num_ratings": 194,
  "book_format": "Kindle版 (電子書籍)",
  "product_url": "https://...",
  "kindle_unlimited": true,
  "delivery": "すぐに購読可能" or "発売予定日は..."
}
```

### 4.5 スコアリング基準

すべて**相対値**(候補10個の中での順位)で算出。絶対値は使わない。

**需要スコア(10点満点)**
- total_products(検索ヒット総数)の多い順に10〜1点
- 直近1年の新刊比率(ASINがB0Gまたは B0Hで始まるKindle本)が高いほど加点

**競合スコア(10点満点)**
- 上位10冊のproduct_num_ratings(レビュー数)中央値の少ない順に10〜1点
- 個人著者比率(ASINがBで始まるKindle専売)が高いほど加点

**意図合致スコア(10点満点)**
- LLMが「上位本タイトル群の読者意図」と「STEP1の草案」の合致度を判定
- 完全一致=10点、ズレ=1点

### 4.6 未発売本のフィルタリング

```javascript
function isReleasedBook(product) {
  if (!product.delivery) return true;
  return !product.delivery.includes("発売予定日");
}
```

### 4.7 出力フォーマット(画面表示)

```
【スコア表】
| キーワード | 需要 | 競合弱 | 意図 | 合計 | AI推奨 |
|------------|------|--------|------|------|--------|
| キーワードA | 9    | 3      | 6    | 18   |        |
| キーワードB | 7    | 7      | 8    | 22   | ★      |
| ...                                                  |

【AIによる総合判定】
✓ 推奨キーワード: 2個 (合計スコア18点以上)
→ STEP3へ進むことを推奨します

または

⚠ 推奨キーワード: 0個 (合計スコア18点以上)
→ STEP1に戻ってコンセプトを調整することを推奨します

【AIからのフィードバック】(STEP1に戻る場合)
- 読者が実際に検索している言葉: 「自分 やりたいこと」「強み 分からない」
- 既存本がカバーできていない切り口: ◯◯
- コンセプト修正の示唆: ターゲットを「◯◯」に絞ると市場性が高まりそうです
```

### 4.8 受講生選定後の出力

**重要**: STEP2の出力は書籍プロファイル確定版を生成しない。STEP3を経て確定アクションで生成される。

## 5. STEP3: 競合レビュー評価(新規)

### 5.1 役割

STEP2で選定したキーワードの上位本のレビューを分析し、読者の不満点・差別化ポイントを抽出する。

**重要1**: STEP3は書籍プロファイルを「確定」しない。市場検証フェーズの第2段階として、差別化分析を行うだけ。STEP3完了後、受講生が明示的な確定アクションを実行する。

**重要2(v4で明確化)**: STEP3は**相談機能を実装しない**。理由はAmazon実レビューに基づく客観分析のため、外部AIで評価できない領域だから。代わりにAI判定アシスト(機械的な判定)で受講生の判断を支援する。

### 5.2 受講生の操作フロー

```
1. STEP2で選定したキーワード・上位本を確認
2. 「深掘り分析実行」ボタンを押す
3. 1〜2分待つ
4. 分析結果を確認
5. 判断:
   5a. 差別化ポイントが明確 → 「書籍プロファイルを確定する」へ進む
   5b. 違和感あり → 「STEP1に戻る」
```

### 5.3 裏側の処理フロー

```
[入力] STEP2で選定したキーワード(1〜2個)+ STEP2で取得済みの上位本ASIN
   ↓
[処理1] 上位3冊のASINを選定
   (レビュー数の多い順、発売済みのみ)
   ↓
[処理2] 各本のTop Product Reviews API呼び出し
   - エンドポイント: 実装時に正確なパス名を再確認
   - パラメータ: asin=ASIN, country=JP
   - 1冊あたり1リクエスト
   ↓
[処理3] 取得データの統合と前処理
   - rating_distribution(★分布の集計値)を抽出
   - レビュー本文を結合
   - ★4〜5レビューと★1〜3レビューを別グループに整理
   ↓
[処理4] LLMで分析
   - 読者の共通不満点(3〜5個)
   - 既存本がカバーできていない切り口
   - 本企画が差別化できるポイント(3個)
   - 注意すべき落とし穴
   ↓
[処理5] 戻り判定アシスト
   - 差別化ポイントが3個以上 → 確定アクションへ進む推奨
   - 差別化ポイントが2個以下 → STEP1に戻る推奨
   ↓
[処理6] STEP1への戻り時フィードバック生成(戻り推奨時)
   ↓
[出力] 分析結果テキスト + 戻り判定結果
```

### 5.4 使用するAPIエンドポイント詳細

**Top Product Reviews**(PoC検証で動作確認済み)

- ベースURL: `https://real-time-amazon-data.p.rapidapi.com`

**必須・推奨パラメータ**

| パラメータ | 値 | 説明 |
|------|------|------|
| asin | ASIN文字列 | 必須 |
| country | `JP` | 日本Amazon |

**注意点**

- ★絞り込みパラメータは持たない(取得後にクライアント側で実施)
- 1リクエストで代表的なレビュー約8件を取得
- 取得されるレビューは★4〜5中心、★1〜3混在の場合あり

### 5.6 LLM分析プロンプト設計

```
あなたはKindle出版の市場分析家です。

【入力情報】
- 本企画の草案: (STEP1の出力)
- 競合本3冊の情報:
  - 本A: タイトル、★分布、レビュー本文
  - 本B: タイトル、★分布、レビュー本文
  - 本C: タイトル、★分布、レビュー本文

【分析タスク】
以下を抽出してください:
```

### 6.7 相談機能の実装(新規・v4で追加)

書籍プロファイル確定アクションには、外部AI相談機能を実装する。既存のSTEP1〜10と同じく`src/DiscussionPanel.jsx`を活用する設計。

**配置場所:**
- 確定版プレビュー画面の下部に「外部AIで相談する用プロンプトを取得」ボタンを配置
- STEP4へ進む前の最終チェックとして機能

**相談機能の6つの観点:**

1. **コンセプトと市場検証の整合性**
   STEP1の主観コンセプトとSTEP2/3の市場データが矛盾していないか。

2. **確定版の網羅性**
   STEP4以降で必要な情報が確定版に揃っているか。

3. **差別化ポイントの具体性**
   抽象論ではなく、本の中身として表現できる具体的な差別化か。

4. **売れる本としての完成度**
   購買動機・差別化・読者の不満解消が組み込まれているか。

5. **マーケ軸との整合**
   コア・ベネフィット+出版目標と市場検証結果が同じ方向を向いているか。

6. **STEP4以降への接続性**
   タイトル設計・章構成・本文・Amazon説明文を作る時に迷わず進めるか。

**レビュープロンプトに同梱する情報:**

`extractDiscussionContext()`の拡張で、以下を自動で同梱する。

```javascript
{
  step1_concept: "STEP1の草案テキスト",
  step2_keywords: "選定された主要検索キーワード",
  step2_competitor_titles: "上位本のタイトル群",
  step3_unmet_needs: "読者の真のニーズ(STEP3抽出)",
  step3_differentiation: "差別化ポイント(STEP3抽出)",
  work_profile_final: "確定版テキスト全文"
}
```

**修正版の反映先:**

外部AIから返ってきた修正版は、以下のいずれかに反映できる。

| 修正対象 | 反映先 |
|---------|--------|
| 確定版テキスト全体 | 確定版プレビュー画面の編集エリア |
| STEP1への修正提案 | STEP1入力欄(戻ってからSTEP2/3を再実行する必要あり) |
| 検索キーワード戦略 | STEP2の選定キーワード(戻って再選定) |

**1回完結原則の適用:**

設計書v4セクション9-2の「1回完結原則」を適用。観点リストにない新角度の批判は後出し不可。

### 6.8 ロック機構

書籍プロファイル確定後、STEP4以降に進むと**書籍プロファイルがロックされる**。

- 編集しようとすると警告ダイアログ表示
- 「ロック解除」ボタンで再編集可能(警告付き)
- STEP1〜3に戻る場合もロック解除が必要

Phase 1Aでは警告ダイアログのみで実装。厳密なロック制御はPhase 2で改善。

### 6.9 確定版の再生成

STEP1に戻って草案を修正した場合、再度STEP2/3を実行→確定アクションを実行する必要がある。

確定版は最新のもののみ保持(`aipub:work_profile`を上書き)。旧版の履歴は保存しない(Phase 1Aでは)。

## 7. 戻りルート設計

### 7.1 戻り先のルール

**戻り先は常にSTEP1のみ**。複雑な分岐は作らない。

```

  ↑         │          │
  └─────────┴──────────┘
       戻る時は全部STEP1へ
```

確定アクション画面からも「STEP1に戻る」「STEP3に戻る」が可能。

### 7.2 戻りルートの基本仕様

**(A) 戻りボタンの配置**
- STEP2の結果画面に「STEP1に戻る」ボタン
- STEP3の結果画面に「STEP1に戻る」ボタン
- 確定版プレビュー画面に「STEP3に戻る」「STEP1に戻る」ボタン
- いずれもAI判定アシストの表示直下に配置

**(B) 戻り時の引き継ぎデータ**
戻る際、戻り元で得られた市場データの示唆を、STEP1画面の上部に表示する。

**(C) STEP1の状態**
戻ってきた時、STEP1のコンセプト内容は前回の値が保持されている。受講生が判断して、必要な箇所だけ手動で修正する。

**(D) 進捗状態の扱い**
STEP1に戻った時点で、STEP2・STEP3の進捗フラグは「未着手」にリセットされる。再度実行する場合はAPIを再消費する。

書籍プロファイルが既に確定されていた場合、STEP1に戻ると確定版はロック解除状態になる(警告表示)。再度確定アクションを実行する必要がある。

## 8. API選定とコスト

### 8.1 採用API確定

**Real-Time Amazon Data**(RapidAPI経由、提供者: FlyByAPIs)

### 8.2 採用判断の根拠(PoC検証結果)

| 検証項目 | 結果 |
|----------|------|

| 日本語キーワード検索 | ◎ 正常動作 |
| 日本語レビュー取得 | ◎ 文字化けなし |
| Product Search の機能 | ◎ 1ページ40〜50件取得可能 |
| Top Product Reviews の機能 | ◎ cookie不要で約8件取得可能 |
| レスポンス速度 | ◎ 数秒以内(体感) |
| 無料枠 | ◎ 月100リクエスト・クレカ不要 |

### 8.3 使用エンドポイントと用途

| エンドポイント | 用途 | パラメータ | 1リクエストあたり取得件数 |
|----------|------|------|------|
| Product Search | STEP2: キーワード評価 | query, country=JP | 約40〜50件の商品 |
| Top Product Reviews | STEP3: レビュー分析 | asin, country=JP | 約8件のレビュー + rating_distribution |

**注**: 通常の`Product Reviews`エンドポイントはcookie必須のため利用しない。

### 8.4 想定リクエスト消費量

**1サイクル(STEP2+STEP3)あたり**
- STEP2 Product Search: 10リクエスト(キーワード10個分)
- STEP3 Top Product Reviews: 3リクエスト(上位3冊分)
- 戻り発生時の再実行も同じ消費量
- **合計: 13リクエスト/サイクル**

**月間試算(受講生10名×月2サイクル+戻り1回平均)**
- 10名 × 3サイクル × 13リクエスト = **390リクエスト/月**

### 8.5 推奨プラン

| プラン | 月額 | リクエスト上限 | 受講生規模 |
|------|------|------|------|
| Basic(無料) | 0円 | 100 | PoC・1〜2名 |
| Pro($14.99) | 約2,300円 | 約10,000 | 〜700名規模(戻り考慮) |

→ **サブスク開始時にProプランへ移行を推奨**

### 8.6 環境変数の設定

```
RAPIDAPI_KEY=[APIキー]
RAPIDAPI_HOST=real-time-amazon-data.p.rapidapi.com
```

Vercelの環境変数に登録。.envファイルはgit管理から除外。

### 8.7 セキュリティ運用

- APIキーは絶対にスクショ・チャット・gitに含めない
- APIキーが漏れた場合は即座にRapidAPIコンソールでローテーション
- 受講生にはAPIキーを見せない(バックエンド経由でのみ使用)

### 8.8 エラーハンドリング

- API障害時: リトライ3回 → 失敗時はエラーメッセージ表示
- レート制限超過: 警告表示、Proプランへの自動切り替え案内
- 検索結果0件: 該当キーワードのスコアを最低値で扱う
- 発売予定日のみの結果: スコア計算から除外
- 戻りルート中のエラー: STEP1の表示は維持し、フィードバック取得失敗のみ通知

```
旧STEP1「完了」→ 新STEP1「未着手」  ※コンセプト出力フォーマット変更のため
旧STEP2(廃止)→ アーカイブ
新STEP2「キーワード絞り込み」→ 「未着手」(新規追加)
新STEP3「競合レビュー評価」→ 「未着手」(新規追加)
旧STEP3「完了」→ 新STEP4「完了」
旧STEP4「完了」→ 新STEP5「完了」
旧STEP5「完了」→ 新STEP6「完了」
旧STEP6「完了」→ 新STEP7「完了」
旧STEP7「未着手」→ 新STEP8「未着手」
旧STEP8「未着手」→ 新STEP9「未着手」
旧STEP9「未着手」→ 新STEP10「未着手」
```

### 9.3 既存ユーザーの扱い: 方針A(任意表示)を採用

すでに先のSTEPを完了している既存ユーザーには、新STEP1〜3を「任意で実行可能」と表示する。強制的に最初からやり直しを要求しない。

```
新STEP1「未着手(任意)」
新STEP2「未着手(任意)」
新STEP3「未着手(任意)」
新STEP4「完了」 ← ここから作業を継続できる
```

理由:
1. 既存受講生1期生4名の作業中断を防ぐ
2. 新機能(STEP2/3)を試したい人だけ試せる
3. 完了したプロジェクトに戻る必要がない

### 9.4 マイグレーションスクリプトの基本仕様

```sql

-- STEP番号の更新(旧STEP3〜9 → 新STEP4〜10)
UPDATE project_steps
SET step_number = step_number + 1
WHERE step_number >= 3 AND step_number <= 9;

-- 旧STEP2の進捗データを削除またはアーカイブ

WHERE step_number = 2 AND archived_at IS NULL;

-- 新STEP2・新STEP3のレコードを追加(任意フラグ付き)

SELECT id, 2, 'not_started', true FROM projects;
```

## 16. 注意事項とリスク

### 16.1 注意事項

- APIキーは絶対にgitに含めない・スクショに映さない
- 受講生に表示するエラーメッセージは平易な日本語にする(ですます調・口語調)
- STEP2/3のAPI呼び出しは時間がかかるため、進捗表示を必ず実装する
- 既存の出力データ(STEP9までの実装済みデータ)を破壊しないこと
- ブランド美学(ネイビー×ゴールド×ホワイト、Noto Sans Japanese、見出し太字)を維持
- STEP4以降のDifyプロンプトは変更しない(書籍プロファイル確定版を参照する設計を維持)

### 16.2 既知のリスク

- **Amazon仕様変更リスク**: 今後Top Product Reviewsも制約を受ける可能性。代替プロバイダ(Unwrangle, SerpApi, Scrapingdog)を念のため把握
- **無料プラン枠超過**: 受講生10名規模で月100リクエストを超える見込み。サブスク開始時にProプラン($14.99/月)へ切り替え必須
- **戻りループのリスク**: 受講生がSTEP1→2→1→2→1→...と無限ループに陥る可能性。戻り回数を内部記録し、3回以上連続戻りの場合は受講生に「個別サポート」を案内する仕組みを検討
- **マイグレーションリスク**: 既存ユーザーの進捗状態が壊れる可能性。必ず検証環境でテスト後、本番反映
- **確定版のフォーマット崩れ**: マークダウン構造が崩れるとSTEP4以降のプロンプトで参照失敗する可能性。LLMプロンプトで構造遵守を強く指示
